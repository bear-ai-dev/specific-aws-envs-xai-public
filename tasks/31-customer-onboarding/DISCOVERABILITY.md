# Discoverability

One row per rule the grader decides on. Every rule has to be reachable by at
least one of three routes: **stated** in `instruction.md`, **derivable** from
code the agent can read in `/app`, or **observable** in the sandbox the agent
can query. Paths below are relative to `/app` unless they start with `/opt`.

The sandbox is queried the way `/opt/meteringco-sandbox/README` suggests: the archive
of last month's provisioning for `biz_apex`, one object per onboarding, under
`s3://meteringco-config-archive-dev/customer-provisioning/2026-08/`. There are six
objects, one per case class the grader distinguishes — see "What the archive
does and does not carry" below. Each object pairs the request and the state it
met with what the reference implementation persisted (`influxWrites`, in line
protocol), recorded (`auditEvents`), published (`webhookEvents`) and returned
(`response`). Every archived row quoted below was produced by running the
reference implementation, not written by hand.

The single most load-bearing survivor is **`OfferingService.create`** in
`src/offering/offering.service.ts:118-190`. It is the sibling of the removed
method: same allowance gate, same `${STAGE}-config` write, same metering block,
same audit fallback, for offerings instead of customers.

## What the archive does and does not carry

The grader distinguishes twenty case classes: three mutually exclusive refusals,
and on the accepted path seven independent binary dimensions (identifier
supplied or generated; rail opened, brought by the caller, or absent; contract
requested or not; prepaid credit present or not; trial present or not; metering
succeeding or failing; usage and the optional columns supplied or not). The
refusals and the three-way rail dimension put the floor at six recordings, and
there are exactly six. `.local/coverage.py` walks the shipped estate and
reports which recording instantiates each class; fourteen classes have exactly
one instance and the six with two are the "absent" halves of a dimension, which
every recording not exercising the positive half is an instance of for free.

Each record keeps its inputs and the outputs that left the service. It does
**not** carry the arguments the reference passed its own collaborators — no
entitlement call, settings read, customer lookup, contract create, enrolment or
metering transcript. Each of those is recoverable from surviving code, cited in
the rows above, and archiving them would hand over a call transcript to copy in
place of a convention to derive. The six rules that consequently have no
`observable` route at all — 2, 4, 8, 13, 14 and 22 — each rest on a signature,
a DTO field or an enum member in the surviving tree that admits one reading.

## Things a reader might expect to be graded and that are not

- The **wording of any message or exception**. Refusals are graded by status
  class only (409 for an exhausted allowance, 400 for a taken identifier and
  for an unconnected business). The reference implementation and an
  independent rewrite with entirely different message text both score 1.0.
- **Where the logic lives.** The verifier calls `CustomerService.create`,
  which the surviving tests pin, and nothing else. The structurally different
  implementation that scores 1.0 puts the whole flow in a new
  `CustomerOnboarding` class in a new file and leaves a two-line delegate
  behind, generates identifiers with `node:crypto` rather than `uuid`, decides
  the payment rail from its own table rather than by calling
  `CustomerEntity.shouldCreateStripeCustomer`, opens the rail customer before
  rather than after the contract, and keeps the onboarding alive through a
  metering failure with `Promise.allSettled` rather than `try`/`catch`.
- **The order of independent steps.** Only orderings with an observable
  consequence are graded: the allowance gate and the identifier check must
  precede any effect, and the announcement must survive a metering failure.
- **Anything the row carries beyond the tags named above** — `metadata`,
  `offeringIds`, `softDelete`, the field set beyond `customerName`.
- **The HTTP layer.** `POST /customers` is not restored by the reference
  solution's grade; the controller route can be put back or not.
- **`CustomerService.remove`, the Stripe Connect onboarding module, the portal
  self-serve route and the dogfood provisioning** were removed with the same
  capability but are not graded — see the honest-limits section of the README.
